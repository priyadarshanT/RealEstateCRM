1. The system at a glance

Users open one web app on computer or phone. Every request goes through Cloudflare, which forwards it to one of two identical app servers in the AWS UAE region. Both servers share one PostgreSQL database that has a live standby copy. Outside services (Meta, WhatsApp, Property Finder, Bayut, Dubizzle, the general webhook, Stripe for subscription payments) send data in through webhooks and receive calls from our background worker. Our own team runs the business from a separate owner console with its own login.

2. What runs on each app server

Both servers run the same five Docker containers. The servers are interchangeable: any request can go to either one, because nothing is stored on the server itself.

4. How a new lead flows through the system

Example: a person fills a Meta lead form. The same path is used for every source; only the adapter in step 3 changes.

1 · RECEIVEMeta calls our webhookPOST /webhooks/metaSignature checked. Event saved to webhook_events. Reply 200 in under 1 s.
2 · QUEUEJob createdqueue: lead-intakeDuplicate event IDs ignored (idempotent).
3 · FETCHMeta adapterWorker fetches full form answers and campaign, ad set, ad, form IDs from Meta API.
4 · SAVEInquiry + leadPhone to E.164, email lower case. Inquiry saved with original answers. New lead created, or enquiry added to the existing lead (re-enquiry → same agent, notified).
5 · ASSIGNAssignment rulesRules top to bottom, round-robin, skip unavailable. No match → Unassigned.
6 · SCOREFirst scoreBudget, project, source quality.
7 · NOTIFYAgent alertedIn-app + push. Welcome WhatsApp sent (P2).
8 · WATCHTimers start10-minute timer starts (next agent, then Admin).
If any step fails: the job retries 5 times with increasing delay, then is marked failed, shows on the Integrations screen and can be retried manually. Nightly Meta reconciliation catches anything missed.

6. Security design

Edge
HTTPS only · Cloudflare firewall and DDoS · rate limits on login and webhooks · no open ports on servers
→
Identity
Cognito login · two-factor required · short-lived access token (1 h) · refresh token
→
Application
Permission + scope check on every request · input validation · webhook signatures verified
→
Data
Row-level security by tenant · encrypted at rest · audit log append-only · secrets in SSM

Figure 4. Four layers of protection. A bug in one layer is still stopped by the next.

  1. Tenant isolation: every business table has tenant_id. The api opens each transaction with the user's tenant, and PostgreSQL row-level security only returns that tenant's rows.
  2. Files: S3 is private. Users get time-limited download links (5 minutes) only for files they are allowed to see.
  3. Owner console: separate Cognito user pool with two-factor login and a separate database role (crm_platform). It can see plans, seats, payments and usage, but no screen or API shows a company's leads or messages. Every action is logged.
  4. Payments: card details go straight from the browser to Stripe; our servers only keep Stripe IDs and the last 4 digits.
  5. Integration tokens (Meta, WhatsApp, portals, Google, Microsoft…) are stored encrypted in SSM Parameter Store, never in the database or code.
  6. Webhooks are accepted only with a valid provider signature or shared secret.
